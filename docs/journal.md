## 2026-11-16 — Dense-поиск через `bge-m3` на сервере (ветка `feat-add-llm`)

**Зачем:** GPU нет, а без dense и hybrid у 56% запросов ни одна стратегия ничего не находит (см. запись от 05.11), и разметка оракула бесполезна. На сервере есть `bge-m3`, поэтому эмбеддинги считаем через API.

**Что сделано**
- [retrievers.py](../src/arag/retrievers.py), класс `APIDenseRetriever`:
  - корпус кодируется через `/v1/embeddings` шардами по 1024 пассажа, параллельно (`dense.workers: 4`);
  - если индексация оборвалась, повторный запуск досчитывает только недостающие шарды;
  - в конце шарды склеиваются в `cache/index/<домен>/dense_api__bge-m3.npy` (fp16) и `.json` с хэшем id пассажей. Индекс от другого корпуса не подхватится молча;
  - матрица в памяти хранится во float32: matmul во fp16 в numpy очень медленный. Это касается и старого локального варианта.
- [llm.py](../src/arag/llm.py): `embed_batch` (без кэша, для корпуса) и `embed_one` (с кэшем в sqlite, для запросов).
- **Latency эмбеддинга запроса** — отдельный этап `embed`, отделён от `retrieve`. При попадании в кэш берётся latency первого вызова, как у LLM.
- **CLI:**
  - новая команда `arag index` строит индексы заранее;
  - `run` для dense и hybrid сначала параллельно считает эмбеддинги запросов;
  - группа стратегий `no_rerank` — все 12 стратегий без reranker;
  - `llm-check` проверяет `bge-m3`: размерность, косинусы на примере, батч максимальной длины.
- `config.yaml` → секция `dense`: `backend: api`, `model: bge-m3`, без префикса запроса, `batch_size: 64`, `max_chars: 8000`.

**Объём:** 366 479 пассажей, около 358 млн символов (примерно 90 млн токенов).

| домен | пассажей | ср. длина, символов |
|---|---|---|
| clapnq | 183 408 | 640 |
| cloud | 72 442 | 1 513 |
| fiqa | 61 022 | 752 |
| govt | 49 607 | 1 708 |

На диске это около 750 МБ (fp16), в памяти при поиске до 750 МБ на clapnq (float32).

**Ограничения**
- Модели `bge-m3` и `bge-base-en-v1.5` в старом README различаются. Наш dense-бейзлайн — `bge-m3`.
- Reranker на сервере отсутствует, поэтому стратегии `+rerank` пока не считаются. Это 12 из 24 стратегий.

**Что запустить**
```bash
source venv/bin/activate && source .env
arag llm-check                                    # 1. проверка bge-m3: должно быть OK для батча max_chars
arag index --domains fiqa                         # 2. самый маленький корпус: оценить время
arag index                                        # 3. остальные домены; если оборвётся, просто перезапустить
arag run --strategies no_rerank                   # 4. 12 стратегий (bm25 уже посчитаны и будут пропущены)
arag eval --slice later_turns
arag oracle
arag significance --baseline last:bm25 --slice later_turns
arag analyze --out docs/results/mtrag_norerank_analysis.md
```

**Результаты:** ещё не запускалось.

## 2026-11-16 — Подключение LLM API лаборатории (ветка `feat-add-llm`)

**Контекст:** получен доступ к LiteLLM-прокси лаборатории `http://10.32.15.88:4000/v1`. Это OpenAI-совместимый API, модель `qwen3.8`. Ключ лежит в `.env` (`LLM_API_KEY`), `.env` в git не попадает.

**Что сделано**
- [llm.py](../src/arag/llm.py):
  - таймаут и повторы при 429, 5xx и таймаутах (`llm.timeout`, `llm.max_retries`);
  - кэш LLM-вызовов безопасен при многопоточном доступе;
  - пустой ответ, обрезанный по длине, не кэшируется;
  - `extra_body` уходит в каждый запрос и входит в ключ кэша;
  - `parse_json` не падает на битом JSON;
  - добавлен `strip_think` для ответа без открывающего `<think>`.
- **Параллельные запросы** (`--workers`, по умолчанию `llm.workers: 8`):
  - `run` сначала параллельно прогревает кэш `llm_rewrite`, потом идёт обычный последовательный проход;
  - `route` считает решения LLM-роутера параллельно;
  - `answer` параллельно генерирует ответы и оценивает их судьёй.
- **Возобновление:** если прогон упал на ошибке API, уже полученные ответы остаются в кэше, и перезапуск продолжает с того же места.
- **Новая команда `arag llm-check`** проверяет подключение без кэша:
  - выводит список моделей;
  - для каждой модели из конфига делает ping, тестовый rewrite и JSON-ответ роутера;
  - сообщает, включено ли у модели thinking и принимает ли сервер `extra_body`.
- [config.yaml](../config.yaml): адрес LiteLLM; все роли временно на `qwen3.8`; thinking у Qwen3 отключён через `extra_body.chat_template_kwargs.enable_thinking: false`.
- `answer` предупреждает, если генератор и судья — одна модель.

**Важно для методики**
- **Latency при `--workers > 1` завышена**, потому что запросы стоят в очереди на сервере. Для замеров стоимости (RQ3) LLM-этапы перезапускать с `--workers 1` на подвыборке. Токены от параллельности не зависят.
- **Судья пока та же модель, что и генератор.** Перед прогоном `answer` нужно выбрать другую модель из `/v1/models`.
- **Кэш привязан к модели, промпту и `extra_body`.** Смена любого из них приводит к новым вызовам.

**Что запустить** (результаты добавить сюда же)
```bash
source venv/bin/activate && source .env
arag llm-check                                                      # 1. подключение, модели, thinking
arag run --strategies llm_rewrite:bm25 --limit 20 --overwrite       # 2. пробный прогон на 20 задачах
arag run --strategies llm_rewrite:bm25 --overwrite                  # 3. полный прогон, 675 LLM-вызовов
arag eval --slice later_turns                                       # 4. llm_rewrite в сравнении с last и gold_rewrite
arag significance --baseline last:bm25 --slice later_turns
```

**Результаты `arag llm-check`:**
- На сервере 4 модели: `qwen3.8`, `gemma-4-26B-A4B-it`, `qwen3-vl-30b` (мультимодальная, нам не нужна), `bge-m3` (эмбеддинги).
- `qwen3.8`: ping 250 мс; rewrite 347 мс, 11 токенов (*«Which is more important: Market Cap or NAV?»*); JSON роутера разобран. Отключение thinking через `extra_body` сервер принимает: thinking в ответе нет.

**Решение по ролям:**
- rewrite и роутер — `qwen3.8`: быстрая, JSON возвращает корректно.
- генератор — `gemma-4-26B-A4B-it`.
- судья — `qwen3.8`, то есть другое семейство моделей, чем генератор.

Повторный `llm-check` прошёл для обеих моделей:
- `qwen3.8`: ping 64 мс, rewrite 56 мс. Первый замер (250 мс) был «холодным».
- `gemma-4-26B-A4B-it`: ping 156 мс, rewrite 198 мс (*«Which is more important, Market Cap or NAV?»*), JSON роутера разобран.

**Решение:** работаем только с двумя моделями, `qwen3.8` и `gemma-4-26B-A4B-it`. Распределение ролей выше.

**Находка:** на сервере есть `bge-m3`. Dense-поиск можно считать через `/v1/embeddings`, без локального GPU. Reranker-модели на сервере нет.

**Результаты прогонов `llm_rewrite`:** ещё не запускалось.

## 2026-11-05 — Анализ данных и BM25-бейзлайнов

**Что сделано**
- Добавлена команда `arag analyze` ([src/arag/analysis.py](../src/arag/analysis.py)). Она строит markdown-отчёт: состав датасета, сравнение последнего вопроса с human rewrite, качество стратегий по срезам, оракул, анализ того, когда rewrite помогает.
- Отчёт по трём BM25-стратегиям на MTRAG (777 задач, 4 домена): [results/mtrag_bm25_analysis.md](results/mtrag_bm25_analysis.md).

**Результаты** (nDCG@5)

1. **Качество падает с номером хода.** На первом ходе 0.335, на 6+ ходе 0.157 у `last`. 35% задач приходятся на 6+ ход, так что многоходовость — основная сложность датасета.
2. **Human rewrite помогает умеренно и не везде.** Для последующих ходов в среднем +0.025 (значимо, p_holm = 0.014). У 69% запросов ничья: обычно обе стратегии дают 0, потому что BM25 ничего не находит.
3. **Выигрыш от rewrite монотонно растёт с дефицитом контекста.** Если rewrite почти не добавляет слов к вопросу, Δ = −0.005. Если вопросу не хватает 2/3 слов rewrite и больше, Δ = +0.077, а nDCG у `last` 0.081 против 0.158 у gold. Именно эту величину роутер должен научиться предсказывать без gold.
4. **Clarification выигрывает от rewrite сильнее Follow-up**: +0.075 против +0.016. Метка `Multi-Turn` на инференсе недоступна, но её можно предсказывать как вспомогательную задачу.
5. **Keyword-вопросы от rewrite проигрывают**: −0.057, 7 побед против 12 поражений. Composite тоже проигрывают (−0.022). Значит, переписывать всегда — плохая стратегия. Это аргумент в пользу роутера.
6. **Эвристика `dependent` из RuleRouter даёт слабый, но правильный сигнал**: Δ от rewrite +0.035 у зависимых вопросов против +0.012 у самостоятельных.
7. **Склейка реплик пользователя (`user_concat`) работает только на 2-м ходе.** Там она равна gold (0.277 против 0.278), а дальше хуже `last`: тема диалога смещается, и старые реплики добавляют шум. Окно истории надо выбирать адаптивно.
8. **Только 54% недостающих слов есть в истории, и лишь 33% — в репликах пользователя.** Значит, ответы агента — важный источник контекста. `user_concat` их не видит, `llm_rewrite` видит.
9. **BM25 слишком слаб для разметки роутера.** У 56% запросов ни одна BM25-стратегия ничего не находит в top-5 (в cloud и fiqa 62–67%). Разметку оракула для обучения строить только после dense, hybrid и reranker.

**Решения**
- Признаки для будущего роутера: оценка дефицита контекста (доля слов вопроса, отсутствующих в истории, длина, местоимения), номер хода, тип вопроса (keyword или полное предложение), лексическое пересечение с последней репликой агента.
- Срез `later_turns` считать основным в отчёте. Первый ход приводить отдельно.

**Что дальше:** dense, hybrid и reranker (нужен GPU или сервер); каркас обучаемого роутера на признаках.
