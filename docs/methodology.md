## Исследовательские вопросы

- **RQ1.** Есть ли смысл выбирать стратегию retrieval для каждого запроса отдельно? Оценивается разрывом между лучшей фиксированной стратегией и оракулом.
- **RQ2.** Помогает ли роутеру история диалога? На MTRAG сравнены исходные конфигурации. Вклад истории отдельно оценён на MTRAG-UN с одинаковым набором действий. [Результаты контрольного эксперимента](results/mtragun.md#контрольное-сравнение-для-rq2)
- **RQ3.** Какой компромисс между качеством и стоимостью даёт адаптивный роутер? Сравниваются метрики поиска и ответов, LLM-токены, число пар для реранкера и задержка.

## Данные

Загрузчик использует четыре домена IBM из `data/mt-rag-benchmark`: `clapnq` (Википедия), `cloud` (документация IBM Cloud), `fiqa` (финансовый форум) и `govt` (сайты госорганов США). Размеры выборок проверены на коммите данных `e0970de`.

| Датасет | Раздел | Всего задач | С qrels | Последующие ходы с qrels |
|---|---|---:|---:|---:|
| `mtrag` | `mtrag-human` | 842 | 777 | 675 |
| `mtragun` | `mtragun-human` | 507 | 332 | 309 |

- **Задача** — один ход пользователя вместе со всей предыдущей историей диалога (`Task.turns`). Последняя реплика — текущий вопрос.
- **qrels** — разметка релевантности пассажей. В оценку поиска и ответов входят 777 задач MTRAG и 332 задачи MTRAG-UN с qrels. Для переноса Adaptive-RAG после исключения общих диалогов оцениваются 303 задачи MTRAG-UN, в том числе 283 последующих хода. В обоих срезах представлены категории `ANSWERABLE` и `PARTIAL`.
- **Human rewrite** (`rewritten_query`) — самостоятельная формулировка вопроса, написанная человеком. В используемом срезе она есть у всех 675 последующих ходов MTRAG с qrels. В файле задач MTRAG-UN, который загружает наш код, это поле пустое. При отсутствии человеческой формулировки режим `gold_rewrite` берёт текущий вопрос. Стратегии с `gold_rewrite` входят в сравнение на MTRAG.
- **Корпуса** — пассажи по 512 токенов с перекрытием 100. Их id совпадают с qrels.
- В истории MTRAG сохранены эталонные ответы агента. Результаты переписывания и генерации относятся к этому виду истории.

## Стратегии

Стратегия записывается как `<query>:<retriever>[+rerank]`.

Пайплайн загружает ход и его историю, формирует поисковый запрос, ищет пассажи и при необходимости меняет их порядок с помощью реранкера. Роутер выбирает конфигурацию для этого хода. Генерация и оценка ответов выполняются отдельной командой по сохранённым результатам поиска. [Загрузка](../src/arag/data.py) · [Поисковый пайплайн](../src/arag/pipeline.py) · [Роутеры](../src/arag/routers.py) · [Генерация и оценка](../src/arag/generation.py)

| Часть | Значения |
|---|---|
| query | `last` — последний вопрос как есть; `user_concat` — три последние реплики пользователя через пробел; `gold_rewrite` — human rewrite; `llm_rewrite` — переписывание LLM по истории (1 вызов); `chiq` — CHIQ-AD (Mo et al., 2024): улучшение истории + переписывание (5–6 вызовов), см. ниже |
| retriever | `bm25` (bm25s, стемминг, стоп-слова); `dense` — `bge-m3` через `/v1/embeddings` сервера лаборатории, cosine по нормированным векторам, пассажи обрезаются до 8000 символов; `hybrid` — RRF по bm25 и dense (top-100 каждого), k=60 |
| `+rerank` | локальный cross-encoder `cross-encoder/ms-marco-MiniLM-L-6-v2` по 50 кандидатам первой стадии. Оценки пар кэшируются. Пилот с более тяжёлой моделью описан в [журнале](journal.md). |

`run --strategies all` перебирает все 30 комбинаций. Группа `no_llm` включает 18 стратегий без LLM-переписывания. Группа `no_rerank` включает 15 стратегий без повторного ранжирования. На MTRAG-UN прогонялись 12 комбинаций `last` и `llm_rewrite` с тремя ретриверами и двумя режимами реранкинга.

**Реализуемая (deployable) стратегия** — любая, кроме `gold_rewrite:*`. Human rewrite на инференсе недоступен, поэтому `gold_rewrite` используется только для сравнения. **Это не потолок**: при dense-поиске `llm_rewrite` имеет более высокий средний nDCG@5 (+0.032, см. журнал за 16.11). Human rewrite в MTRAG минимальный: он только делает вопрос самостоятельным и не расширяет его. Поэтому в тексте работы — «human rewrite baseline».

**Стоимость стратегии** (`cost_rank` в `cli.py`) — сумма условных весов для выбора оракула. `llm_rewrite` = 3, `chiq` = 6, `dense` = 1, `hybrid` = 1.5, `rerank` = 2, остальные компоненты имеют вес 0. Измеренные задержки, токены и число пар для реранкера пишутся в каждый run.

## CHIQ-AD (бейзлайн из плана)

Реализация ad-hoc варианта CHIQ ([arXiv 2406.05013](https://arxiv.org/abs/2406.05013), код авторов [fengranMark/CHIQ](https://github.com/fengranMark/CHIQ)) в `src/arag/queries.py`. Шаги (раздел 3.3 статьи):

1. **Topic Switch** — продолжает ли вопрос текущую тему. Если нет, от истории остаётся последняя пара «вопрос — ответ».
2. **Question Disambiguation** — самодостаточная версия текущего вопроса.
3. **Response Expansion** — последний ответ агента переписывается в развёрнутое предложение (< 20 слов) и заменяет его в истории.
4. **Pseudo Response** — однофразовый ответ LLM на текущий вопрос.
5. **History Summary** — краткое изложение улучшенной истории, только если тема не сменилась.
6. **Переписывание** вопроса в поисковый запрос по улучшенной истории, JSON `{"query": ...}`.

- **Поисковый запрос** = rewrite + pseudo response + disambiguated question, как в прогонах авторов `search_query+single_response+explain_question`. **Запрос для reranker** — только rewrite.
- **Промпты:** инструкции взяты из `PROMPT_DICT` в репозитории авторов. `new_topic` восстановлен по описанию.
- **Модель:** у авторов LLaMA-2-7B-chat, у нас `qwen3.8`, как и для `llm_rewrite`.
- **Отличия от оригинала:**
  - ответы агента в истории обрезаются до 600 символов, потому что в MTRAG они длинные;
  - к промпту Pseudo Response добавлено разрешение отвечать из общих знаний: без него `qwen3.8` в ~56% случаев (пилот) отвечала «context does not contain…»;
  - псевдо-ответ, похожий на отказ, в запрос не добавляется.
- **Не реализованы:** CHIQ-FT (требует дообучения FlanT5 на псевдо-запросах) и CHIQ-Fusion (объединяет AD и FT).

## Оракул

Для каждого запроса берётся лучшая по метрике (`ndcg_cut_5`) стратегия из уже посчитанных runs.

| Вариант | Поле в `runs/<ds>_oracle.jsonl` | Смысл |
|---|---|---|
| По стратегиям, доступным при инференсе | `best` | Лучшая по qrels стратегия без `gold_rewrite`, при ничьей — более дешёвая. Adaptive-RAG строит собственные метки по прогонам трёх уровней. |
| Cost-aware | `best_cheap` | Самая дешёвая стратегия, у которой метрика не ниже `best − eps` (`--eps`, по умолчанию 0.05). Разметка для роутера, который экономит ресурсы. |
| С gold | `best_with_gold` | Лучшая среди всех стратегий, включая `gold_rewrite`. Только верхняя граница. |

**Unsolvable** — запрос, на котором у всех стратегий метрика равна 0. Для такого запроса роутеру нечему учиться, и при обучении его стоит исключать или считать отдельно.

## Метрики

- **Retrieval**: Recall@k и nDCG@k, k ∈ {1, 3, 5, 10}, считаются через pytrec_eval так же, как в официальном скрипте MTRAG. Основная метрика — nDCG@5.
- **Стоимость**: latency по этапам в мс: query (rewrite), embed (эмбеддинг запроса через API), retrieve (поиск по индексу), rerank, router. При попадании в кэш берётся latency первого вызова. Также LLM-токены (prompt + completion), число пар для reranker.
- **Ответы**: correctness, faithfulness, completeness по шкале 1–5 от LLM-судьи, см. раздел «Качество ответов и LLM-as-a-Judge».
- **Токены системы** складываются из токенов переписывания, роутера и генерации. Токены судьи относятся к стоимости оценки и выводятся отдельно. Измерения задержки реранкера зависят от оборудования, поэтому в выводах о стоимости также указываем число обработанных пар.

## Качество ответов и LLM-as-a-Judge

**Генерация** (`arag answer`): `gemma-4-26B-A4B-it` получает последние 6 реплик диалога и top-5 пассажей системы (каждый обрезан до 1500 символов). Инструкция: отвечать только по пассажам, а если ответа в них нет — сказать об этом.

Судья `qwen3.8` получает диалог, те же пассажи, что и генератор, эталонный ответ из выбранного датасета и ответ системы. Он выставляет три оценки по шкале 1–5.

| критерий | с чем сравнивается | что значит 5 |
|---|---|---|
| correctness | эталонный ответ | полностью согласуется с эталоном, ошибок нет |
| faithfulness | найденные пассажи | каждое утверждение подтверждается пассажами; ответ-отказ считается полностью faithful |
| completeness | эталонный ответ | покрыты все ключевые пункты эталона |

- Если судья вернул неполный или некорректный JSON, ответ исключается из средних оценок. В сводке `n` показывает число ответов, а `judged` — число ответов с валидными оценками. Получены 6991 из 6993 оценок на MTRAG и 2626 из 2627 на MTRAG-UN.
- `declined` — доля ответов-отказов («не могу ответить по доступной информации»), определяется регулярным выражением.
- Оценка ответов проводится по сохранённым поисковым прогонам на задачах с qrels.
- **Faithfulness на последующих ходах близка к верхней границе шкалы** (4.97–5.00 на MTRAG и 4.948–5.000 на MTRAG-UN). Поскольку ответ-отказ получает 5 по этому критерию, faithfulness рассматривается вместе с долей отказов. Для сравнения качества ответов информативнее correctness и completeness.
- Faithfulness считается относительно пассажей, которые нашла сама система. Поэтому при плохом поиске ответ может быть faithful, но неверным; поиск оценивается по nDCG и Recall, а correctness и completeness характеризуют итоговый ответ.

**Калибровка судьи** (`arag judge-calibrate`): в MTRAG есть 477 ответов (159 задач × эталон, Llama-3.1-405B, GPT-4o) с оценками трёх аннотаторов по шкале 1–4: faithfulness, completeness, appropriateness, naturalness и win-rate. Судья оценивает эти же ответы, и считается ранговая корреляция (Спирмен, Кендалл) его оценок с медианой аннотаторов. Для ориентира та же корреляция считается для автоматических метрик авторов MTRAG (`rb_llm`, `rl_f`, `rb_agg`), которые уже есть в файле. Определения критериев у людей и у нашего судьи не идентичны: человеческая completeness оценивается относительно контекста, наша — относительно эталона.

В [калибровке v2](results/judge_calibration_qwen_v2.md) корреляция Спирмена по faithfulness составила 0.56 на всех 477 ответах и 0.63 на 318 ответах без эталонов. Для human completeness и completeness судьи значения составили 0.33 и 0.46 соответственно. Эти результаты относятся к MTRAG.

**Значимость**: `arag answers-summary --baseline <система>` — те же парные bootstrap и рандомизационный тест с поправкой Холма, что и для поиска, по оценкам судьи на общих задачах.

## Срезы

- `first_turn` / `later_turns` — номер хода пользователя: 1 или больше 1. Основной срез — `later_turns`, потому что на первом ходе история пуста и все query modes совпадают.
- По меткам MTRAG: домен, `Multi-Turn` (Follow-up / Clarification), `Answerability`, первая метка `Question Type`.
- `dependent` — эвристика RuleRouter: в последующем ходе есть местоимение или анафора, вопрос короче 4 слов или нет вопросительной формы.

## Значимость

`arag significance` сравнивает каждую систему с baseline по общим запросам. Среднее взвешивает каждый ход одинаково. На MTRAG 675 последующих ходов относятся к 110 диалогам, на MTRAG-UN в выборке по одному ходу на диалог:

- **Парный bootstrap** (10 000 выборок диалогов с возвращением, со всеми их парными ходами) даёт Δ среднего и 95% доверительный интервал.
- **Парный рандомизационный тест** (меняем знак всех парных разностей одного диалога вместе) даёт двусторонний p-value.
- **Поправка Холма–Бонферрони** применяется ко всем сравнениям в одной таблице.

При сравнении нескольких систем разница считается значимой, если `p_holm < 0.05` и доверительный интервал не содержит 0. Для заранее выбранной пары RQ2 в отчёте приведены исходные p-значения двусторонних парных тестов.

## Роутеры (этап 4)

Сравниваются три режима из плана плюс верхние границы.

| режим | роутер | что видит | что решает |
|---|---|---|---|
| фиксированный пайплайн | `fixed` | — | одна стратегия для всех запросов. `last:hybrid+rerank` используется по умолчанию. `llm_rewrite:dense+rerank` выбран по MTRAG как основа сравнения на обоих датасетах. |
| адаптация без истории | `adaptive_rag` (бейзлайн Adaptive-RAG) | только последний вопрос | уровень сложности A/B/C → `last:dense` / `last:dense+rerank` / `llm_rewrite:dense+rerank` |
| адаптация без истории | `llm_nohist` | только последний вопрос | ретривер, reranker |
| адаптация без истории (контроль RQ2) | `llm_nohist_rewrite` | текущий вопрос и пустое поле истории | переписывание, ретривер, reranker |
| адаптация с историей | `llm_hist` | вопрос и последние 6 реплик | переписывание, ретривер, reranker |
| адаптация с историей, эвристики | `rule` | вопрос и наличие истории | переписывание (если вопрос зависит от контекста); dense + reranker всегда |
| верхняя граница | `oracle`, `oracle_cheap` | разметку оракула | лучшая / самая дешёвая из почти лучших стратегий |

- **Стоимость роутера** добавляется к стоимости выбранной стратегии. Для LLM-роутеров учитываются токены и задержка LLM-вызова. Для Adaptive-RAG учитывается задержка получения эмбеддинга вопроса.
- **Доля переписываний** считается только среди последующих ходов: на первом ходе `llm_rewrite` = `last`, и LLM не вызывается.
- Правила `rule` выведены из анализа MTRAG и проверены на MTRAG-UN. [Результаты проверки](results/mtragun.md)
- **Сравнение для RQ2.** `llm_hist` и `llm_nohist` различаются промптами и доступными действиями. Разница 0.039 nDCG@5 на последующих ходах MTRAG относится ко всей конфигурации. В контрольной паре `llm_hist` и `llm_nohist_rewrite` используют одинаковые модель, инструкцию и набор действий. Меняется только поле истории: у первого в нём до шести предыдущих реплик, у второго — `(empty)`. Переписыватель и генератор получают историю в обоих вариантах согласно их обычным настройкам. Основной срез — последующие ходы одних и тех же диалогов. [Команды сравнения](results/mtragun.md#контрольное-сравнение-для-rq2)

## Adaptive-RAG (бейзлайн из плана)

Jeong et al., NAACL 2024. Классификатор сложности запроса выбирает пайплайн возрастающей стоимости. Перенос на нашу задачу (`AdaptiveRAGRouter` в `src/arag/routers.py`, параметры в `config.yaml` → `routers.adaptive_rag`):

| | оригинал | у нас |
|---|---|---|
| вход классификатора | только запрос | только последний вопрос (без истории) |
| уровни A / B / C | без поиска / одношаговый поиск / многошаговый (IRCoT) | `last:dense` / `last:dense+rerank` / `llm_rewrite:dense+rerank` |
| метка для обучения | самый простой уровень, ответивший правильно | самый простой уровень с максимальным nDCG@5 (`eps = 0`) |
| запросы без метки | метка по типу датасета (single-/multi-hop) | не участвуют в обучении |
| классификатор | дообученный T5-large | логистическая регрессия на эмбеддингах `bge-m3` (C = 1.0) |
| оценка | отдельный train/test | 5-fold GroupKFold по диалогам либо обучение на MTRAG и применение к MTRAG-UN |

- Уровня «без поиска» нет: мы оцениваем retrieval, и у такого уровня nDCG был бы равен 0.
- Уровень C использует историю внутри пайплайна (переписывание), но **решение роутера принимается без истории**. В этом отличие от `llm_hist` и `rule`.
- **Стоимость роутера:** эмбеддинг вопроса (тот же, что нужен dense-поиску по `last`) плюс классификатор (~0). В сводке записывается задержка эмбеддинга как время роутера, даже когда downstream dense-поиск переиспользует этот вектор.
- **Перенос с MTRAG.** Команда `arag route --router adaptive_rag --dataset mtragun --train-dataset mtrag` обучается на задачах MTRAG с qrels из всех доменов. Метки берутся из сохранённых прогонов трёх уровней MTRAG. На целевом датасете классификатор использует только эмбеддинг текущего вопроса. Его разметка нужна для оценки поиска. Источник обучения и целевой датасет должны быть разными. Из оценки переноса исключаются целевые диалоги с общим ID или совпадающим текстом первой реплики (после приведения регистра и нормализации пробелов) с любой задачей исходной выборки с qrels. Такое правило исключает также разговоры с одинаковым началом и разным продолжением. Прогон сохраняется как `adaptive_rag_from_mtrag.jsonl`; запуск без `--train-dataset` использует кросс-валидацию внутри выбранного датасета. [Результаты переноса](results/mtragun.md)

Группа для `GroupKFold` — часть `task_id` перед `<::>`, идентификатор диалога. Разбиение по группам удерживает ходы одного диалога в одном фолде.

## Показатели в анализе rewrite (`arag analyze`, раздел 2)

Считаются по контентным токенам: нижний регистр, без стоп-слов и вопросительных слов.

- **Jaccard** — пересечение токенов последнего вопроса и rewrite, делённое на их объединение.
- **Дефицит** — доля токенов rewrite, которых нет в последнем вопросе. Показывает, сколько контекста человек «дописал».
- **Недостающие токены в истории** — какую долю дефицита в принципе можно найти в предыдущих репликах: во всех или только в репликах пользователя.
