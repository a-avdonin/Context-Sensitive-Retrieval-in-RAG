# Методика

## Исследовательские вопросы

- **RQ1.** Есть ли смысл выбирать стратегию retrieval для каждого запроса отдельно? Оценивается разрывом между лучшей фиксированной стратегией и оракулом.
- **RQ2.** Помогает ли роутеру история диалога? Сравниваются роутеры с историей и без неё при прочих равных.
- **RQ3.** Какой компромисс качество / стоимость даёт адаптивный роутер? Оценивается по Pareto-кривой, где стоимость — latency и LLM-токены.

## Данные

MTRAG (IBM, `data/mt-rag-benchmark`), часть `mtrag-human`: 842 задачи, 110 диалогов, 4 домена (clapnq — Википедия, cloud — документация IBM Cloud, fiqa — финансовый форум, govt — сайты госорганов США).

- **Задача** — один ход пользователя вместе со всей предыдущей историей диалога (`Task.turns`). Последняя реплика — текущий вопрос.
- **qrels** есть у 777 задач. У UNANSWERABLE и CONVERSATIONAL задач их нет, поэтому оценка retrieval идёт только на ANSWERABLE и PARTIAL.
- **Human rewrite** (`rewritten_query`) — самостоятельная формулировка вопроса, написанная человеком. Есть у всех later-задач с qrels, на первом ходе отсутствует (там он не нужен).
- **Корпуса** — пассажи по 512 токенов с перекрытием 100. Их id совпадают с qrels.

## Стратегии

Стратегия записывается как `<query>:<retriever>[+rerank]`.

| Часть | Значения |
|---|---|
| query | `last` — последний вопрос как есть; `user_concat` — три последние реплики пользователя через пробел; `gold_rewrite` — human rewrite; `llm_rewrite` — переписывание LLM по истории (1 вызов); `chiq` — CHIQ-AD (Mo et al., 2024): улучшение истории + переписывание (5–6 вызовов), см. ниже |
| retriever | `bm25` (bm25s, стемминг, стоп-слова); `dense` — `bge-m3` через `/v1/embeddings` сервера лаборатории, cosine по нормированным векторам, пассажи обрезаются до 8000 символов; `hybrid` — RRF по bm25 и dense (top-100 каждого), k=60 |
| `+rerank` | локальный cross-encoder (модель выбирается пилотом: `ms-marco-MiniLM-L-6-v2` или `bge-reranker-v2-m3`) по top-50 кандидатам первой стадии; оценки пар кэшируются, latency — время первого расчёта |

**Реализуемая (deployable) стратегия** — любая, кроме `gold_rewrite:*`. Human rewrite на инференсе недоступен, поэтому `gold_rewrite` используется только для сравнения. **Это не потолок**: при dense-поиске `llm_rewrite` значимо лучше (+0.032, см. журнал за 16.11). Human rewrite в MTRAG минимальный: он только делает вопрос самостоятельным и не расширяет его. Поэтому в тексте работы — «human rewrite baseline».

**Стоимость стратегии** (`cost_rank` в `cli.py`) — условный ранг для разрешения ничьих: `llm_rewrite` = 3, `dense` = 1, `hybrid` = 1.5, `rerank` = 2, остальное 0. Реальная стоимость (latency, токены, пары для reranker) пишется в каждый run.

## CHIQ-AD (бейзлайн из плана)

Реализация ad-hoc варианта CHIQ ([arXiv 2406.05013](https://arxiv.org/abs/2406.05013), код авторов [fengranMark/CHIQ](https://github.com/fengranMark/CHIQ)) в `src/arag/queries.py`. Шаги (раздел 3.3 статьи):

1. **Topic Switch** — продолжает ли вопрос текущую тему. Если нет, от истории остаётся последняя пара «вопрос — ответ».
2. **Question Disambiguation** — самодостаточная версия текущего вопроса.
3. **Response Expansion** — последний ответ агента переписывается в развёрнутое предложение (< 20 слов) и заменяет его в истории.
4. **Pseudo Response** — однофразовый ответ LLM на текущий вопрос.
5. **History Summary** — краткое изложение улучшенной истории, только если тема не сменилась.
6. **Переписывание** вопроса в поисковый запрос по улучшенной истории, JSON `{"query": ...}`.

- **Поисковый запрос** = rewrite + pseudo response + disambiguated question, как в прогонах авторов `search_query+single_response+explain_question`. **Запрос для reranker** — только rewrite.
- **Промпты:** инструкции взяты из `PROMPT_DICT` в репозитории авторов. `new_topic` восстановлен по описанию.
- **Модель:** у авторов LLaMA-2-7B-chat, у нас `qwen3.8`, как и для `llm_rewrite`.
- **Отличия от оригинала:**
  - ответы агента в истории обрезаются до 600 символов, потому что в MTRAG они длинные;
  - к промпту Pseudo Response добавлено разрешение отвечать из общих знаний: без него `qwen3.8` в ~56% случаев (пилот) отвечала «context does not contain…»;
  - псевдо-ответ, похожий на отказ, в запрос не добавляется.
- **Не реализованы:** CHIQ-FT (требует дообучения FlanT5 на псевдо-запросах) и CHIQ-Fusion (объединяет AD и FT).

## Оракул

Для каждого запроса берётся лучшая по метрике (`ndcg_cut_5`) стратегия из уже посчитанных runs.

| Вариант | Поле в `runs/<ds>_oracle.jsonl` | Смысл |
|---|---|---|
| Реализуемый | `best` | Лучшая стратегия без `gold_rewrite`, при ничьей — более дешёвая. **Это разметка для обучения роутера.** |
| Cost-aware | `best_cheap` | Самая дешёвая стратегия, у которой метрика не ниже `best − eps` (`--eps`, по умолчанию 0.05). Разметка для роутера, который экономит ресурсы. |
| С gold | `best_with_gold` | Лучшая среди всех стратегий, включая `gold_rewrite`. Только верхняя граница. |

**Unsolvable** — запрос, на котором у всех стратегий метрика равна 0. Для такого запроса роутеру нечему учиться, и при обучении его стоит исключать или считать отдельно.

## Метрики

- **Retrieval**: Recall@k и nDCG@k, k ∈ {1, 3, 5, 10}, считаются через pytrec_eval так же, как в официальном скрипте MTRAG. Основная метрика — nDCG@5.
- **Стоимость**: latency по этапам в мс: query (rewrite), embed (эмбеддинг запроса через API), retrieve (поиск по индексу), rerank, router. При попадании в кэш берётся latency первого вызова. Также LLM-токены (prompt + completion), число пар для reranker.
- **Ответы** (позже): correctness, faithfulness, completeness по шкале 1–5 от LLM-судьи, который предварительно калибруется на human-оценках MTRAG.

## Срезы

- `first_turn` / `later_turns` — номер хода пользователя: 1 или больше 1. Основной срез — `later_turns`, потому что на первом ходе история пуста и все query modes совпадают.
- По меткам MTRAG: домен, `Multi-Turn` (Follow-up / Clarification), `Answerability`, `Question Type`.
- `dependent` — эвристика RuleRouter: в последующем ходе есть местоимение или анафора, вопрос короче 4 слов или нет вопросительной формы.

## Значимость

`arag significance` сравнивает каждую систему с baseline по одним и тем же запросам:

- **Парный bootstrap** (10 000 ресэмплов запросов) даёт Δ среднего и 95% доверительный интервал.
- **Парный рандомизационный тест** (случайно меняем местами a и b внутри пары) даёт двусторонний p-value.
- **Поправка Холма–Бонферрони** применяется ко всем сравнениям в одной таблице.

Разница считается значимой, если `p_holm < 0.05` и доверительный интервал не содержит 0.

## Роутеры (этап 4)

Сравниваются три режима из плана плюс верхние границы.

| режим | роутер | что видит | что решает |
|---|---|---|---|
| фиксированный пайплайн | `fixed` | — | одна стратегия для всех запросов: `last:dense`, `last:hybrid+rerank` (бейзлайн из плана), `llm_rewrite:dense+rerank` (лучшая фиксированная) |
| адаптация без истории | `adaptive_rag` (бейзлайн Adaptive-RAG) | только последний вопрос | уровень сложности A/B/C → `last:dense` / `last:dense+rerank` / `llm_rewrite:dense+rerank` |
| адаптация без истории | `llm_nohist` | только последний вопрос | ретривер, reranker |
| адаптация с историей | `llm_hist` | вопрос и последние 6 реплик | переписывание, ретривер, reranker |
| адаптация с историей, эвристики | `rule` | вопрос и наличие истории | переписывание (если вопрос зависит от контекста); dense + reranker всегда |
| верхняя граница | `oracle`, `oracle_cheap` | разметку оракула | лучшая / самая дешёвая из почти лучших стратегий |

- **Стоимость роутера** — его LLM-вызов (токены и latency), он добавляется к стоимости выбранной стратегии.
- **Доля переписываний** считается только среди последующих ходов: на первом ходе `llm_rewrite` = `last`, и LLM не вызывается.
- **Ограничение rule-роутера:** его принципы выведены из анализа тех же данных MTRAG. Пороги не подбирались, но честная проверка — на MTRAG-UN.

## Adaptive-RAG (бейзлайн из плана)

Jeong et al., NAACL 2024. Классификатор сложности запроса выбирает пайплайн возрастающей стоимости. Перенос на нашу задачу (`AdaptiveRAGRouter` в `src/arag/routers.py`, параметры в `config.yaml` → `routers.adaptive_rag`):

| | оригинал | у нас |
|---|---|---|
| вход классификатора | только запрос | только последний вопрос (без истории) |
| уровни A / B / C | без поиска / одношаговый поиск / многошаговый (IRCoT) | `last:dense` / `last:dense+rerank` / `llm_rewrite:dense+rerank` |
| метка для обучения | самый простой уровень, ответивший правильно | самый простой уровень с максимальным nDCG@5 (`eps = 0`) |
| запросы без метки | метка по типу датасета (single-/multi-hop) | не участвуют в обучении |
| классификатор | дообученный T5-large | логистическая регрессия на эмбеддингах `bge-m3` (C = 1.0) |
| оценка | отдельный train/test | 5-fold GroupKFold по диалогам; каждая задача предсказывается моделью, не видевшей её диалог |

- Уровня «без поиска» нет: мы оцениваем retrieval, и у такого уровня nDCG был бы равен 0.
- Уровень C использует историю внутри пайплайна (переписывание), но **решение роутера принимается без истории**. В этом отличие от `llm_hist` и `rule`.
- **Стоимость роутера:** эмбеддинг вопроса (тот же, что нужен dense-поиску по `last`) плюс классификатор (~0).

## Обучаемый роутер (вне плана, опционально)

Разбиение train/test **только по диалогам** (`GroupKFold` по `conversation_id`, это часть `task_id` до `<::>`). Ходы одного диалога очень похожи, и случайное разбиение по задачам даст утечку.

## Показатели в анализе rewrite (`arag analyze`, раздел 2)

Считаются по контентным токенам: нижний регистр, без стоп-слов и вопросительных слов.

- **Jaccard** — пересечение токенов последнего вопроса и rewrite, делённое на их объединение.
- **Дефицит** — доля токенов rewrite, которых нет в последнем вопросе. Показывает, сколько контекста человек «дописал».
- **Недостающие токены в истории** — какую долю дефицита в принципе можно найти в предыдущих репликах: во всех или только в репликах пользователя.
